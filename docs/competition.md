# AMD 3.1 竞赛规则解读与当前结果评估

核对日期：2026-09-11。适用范围：FPGA 创新设计赛道中 AMD 3.1 的 RTL 方向。

**当前结论：109/156（69.87%）是可用的初版公开集结果，尚不足以证明比赛竞争力。**
本项目已经完成双 4B 在 NVIDIA 上的完整运行；比赛还需要同模型基线增益、
Vivado 分级评测、私有题集泛化、AMD 离线部署和技能包贡献等证据。

## 2. 109/156 到底说明什么

### 2.1 已经实测的内容

| 指标 | 本次结果 | 能说明的范围 |
| --- | ---: | --- |
| 实际执行题目 | 156/156 | 整条工程流程已完整跑一遍，无漏跑 |
| 原始独立功能判定 | 109 PASS / 47 FAIL | 固定公开 VerilogEval v2 的 Icarus 编译与仿真结果 |
| 原始通过占比 | 69.87% | 每题一次完整 ChipMATE 工作流的最终候选通过占比 |
| 执行 ERROR / NOT_RUN | 0 / 0 | 本轮没有执行错误或漏跑 |
| 总耗时 | 10825.27 秒，约 3 小时 | 旧 NVIDIA 服务器上的本轮墙钟时间 |
| 显存采样最大值 | 30201 MiB，约 29.49 GiB | 一秒采样观测值，不保证捕捉所有瞬时峰值 |
| Vivado 编译、仿真、综合 | 未测 | 不能用 Icarus PASS 推定 |
| 同模型裸跑增益 | 未测 | 尚不能证明智能体提升了多少 |
| pass@5 与重复运行稳定性 | 未测 | 内部多候选与多轮重试不能当成 5 次独立运行 |
| AMD W7900 / R9700 | 未测 | NVIDIA 运行不能替代 ROCm 验收 |

证据：[全量结果与评测器对照](journal/20260911_193029_full_suite_results.md)、
[原始评估汇总](../runs/20260911_140717_full_suite_session/assessment.json)。
完整 runs/ 不进入 Git；新 clone 查阅原始产物需要另行同步，本仓库 journal 保留轻量结论。

### 2.2 与作者报告相比

固定版本的 [ChipMATE README](https://github.com/zhongkaiyu/ChipMATE/blob/d94087b5159aea482648b26398a2ffb164246671/README.md)
报告双 4B 在 VerilogEval v2 上的 pass@1 / pass@5 为 **75.0% / 76.3%**。
我们本轮 69.87% 在数值上比 75.0% 低约 **5.13 个百分点**。

但作者按每题 10 次独立完整工作流运行计算 pass@k；
我们只有每题一次完整工作流，评测器适用性也存在下述已知问题。
因此这只是定位差距的参考，不能当作同条件复现结论，
不能宣称已经达到作者结果，也不能据此断言方案失效。
本轮更不适合与表中的其他模型做跨协议排名。

我的工程判断是：已经有可继续迭代的开发起点，相对作者报告仍有差距；
目前没有同口径基线、赛事私有集成绩或官方榜单依据，无法判断获奖档次。

### 2.3 47 个 FAIL 如何理解

| 原始失败类别 | 数量 |
| --- | ---: |
| 输出不匹配 | 35 |
| 编译失败 | 10 |
| 官方测试台超时 | 2 |
| 合计 | 47 |

同一服务器上将官方参考实现作为候选进行 CPU 对照，结果为 151 PASS / 5 FAIL：

- Prob082_lfsr32、Prob141_count_clock：参考实现零不匹配时测试台仍触发时限。
- Prob099_m2014_q6c：参考端口与测试台接口不一致。
- Prob151_review2015_fsm、Prob156_review2015_fancytimer：参考枚举转换不受 Icarus 11 支持。

这五题需要评测条件诊断，不能直接全部归因于模型；
也不能反过来把五题自动判为模型正确、从分母删掉或给原结果补分。
另有 **42 个失败题的参考实现对照通过**，所以差距并不只是评测环境造成的。
原始 109/156 必须保留；修正评测条件应产生新版本与新报告。

还有 12 个原始 FAIL 在上游自验证中达到一致率 1.0。
这说明双模型一致不能替代独立正确性判定，是后续诊断和技能包验证的重要切入点。

## 3. 比赛如何评分

指南 3.1.5.5（印刷第 9 页）给出：

| 评分项 | 权重 | 对我们意味着什么 |
| --- | ---: | --- |
| 能力：题集加权通过率 | 30 | 提高官方各级判定通过率，尤其是可综合的最终结果 |
| 增益：相对同模型裸跑基线的提升 | 40 | 需要测出智能体与技能包相对同一模型直接生成的提升 |
| 代价：墙钟效率 | 10 | 单题与总耗时有价值，要计入工具调用、重试等成本 |
| 智能体与技能包的工程质量 | 20 | 要有清晰设计、失败诊断、可复用技能及效果证据 |
| 合计 | 100 | 具体计分函数仍以评分细则为准 |

**增益项权重高于绝对通过率项。**
一个结果较高但相对裸跑几乎没有提升的方案，不一定比结果略低但增益明确的方案更有优势；
实际名次仍由完整评分公式和其他项共同决定。

指南尚不足以推出增益使用百分点差、相对比例还是归一化公式，
也不能确定题目难度、分级通过率和 pass@k 如何加权。
不能用 69.87% 直接当总分，也不能默认能力得分就是 30 × 69.87%。

## 4. 同模型基线是必须补齐的部分

指南 3.1.5.2（印刷第 8 页）要求：

- run_baseline.sh 与 run.sh 使用同一推理服务、同一上下文配置。
- 基线绕过智能体与技能包，提示词只含题目本身。
- 单次直接生成，不重试、不调用工具。
- 基线与智能体结果须在同一次运行中产出。

“基线生成不调用工具”和“赛事方评测最终代码”是两个阶段；
不能把后续独立评分误当作基线生成期间调用工具。

对本方案的工程解读：

1. 若 RTL 主模型为固定版本 ChipMATE-V-4B，开发时应以同一 V-4B 的单次生成作为匹配对照。
   Qwen 基座或另一个 9B 模型的结果可用于选型，不能直接替代这个同模型对照。
2. 双模型 V/P 体系怎样定义官方“同模型、同推理服务”，仍需赛事方明确。
   单 V-4B 是合理的开发对照设计，不代表官方已批准其为双模型正式基线。
3. 单 9B 若成为最终提交主模型，也要配置对应的同模型裸跑入口和增益实验。
4. 当前 run_baseline.sh 已有调用同一 V 服务、单次生成、客户端不重试的代码；
   但没有与智能体统一运行后独立评分的完整实验，也没有正式输入输出协议验收。
   文件存在不等于这一项已经完成。
5. 用户已决定将单 4B、单 9B 测试推迟到 A100，继续遵守；**推迟不是取消比赛需要的基线**。
   后续在相同硬件、数据和评测器上比较，并记录各方案生成预算和运行配置。

官方还需明确双模型的 P 服务是否在裸跑时保留加载，
以及模型初始化、工具执行、失败重试等时间如何计入同次评测。

## 5. Vivado 是最终判定链的一部分

指南 3.1.2（印刷第 7 页）规定 RTL 按以下顺序评测，前一级通过后才进入下一级：

| 级别 | 工具与条件 |
| --- | --- |
| 可编译 | Vivado 2025.2 的 xvlog 与 xelab 成功 |
| 仿真通过 | xsim 运行参考测试台，逐拍比较无差异 |
| 可综合 | 针对 xczu3eg-sbva484-1-e，synth_design 生成网表且无 ERROR |

统一目标器件为 xczu3eg-sbva484-1-e，时钟约束为 5 ns。

**Icarus 功能通过尚未覆盖比赛的上述三级条件。**
仿真正确也不自动意味着可综合。指南提到 5 ns，但没有在这段定义完整布局布线、
时序收敛或 PPA 的计分门槛，不能自行扩写成已明确的评分条件。

按照现有项目安排，Vivado 实施仍是后续工作；本次规则解读不启动安装或测试。
后续应复用生成的 RTL，分别保存三阶段日志和分级结果，
形成开发用 Icarus 与比赛用 Vivado 的可追溯对照。

### Icarus 依赖需要单独确认

指南 3.1.3.2 说赛事方固定基础镜像和 EDA 工具链，只提供 Vivado/Vitis，不含第三方工具。
当前 ChipMATE 内部交叉验证和本地独立评测都使用 Icarus。

这意味着不能假设官方镜像自带 Icarus。
“未提供”也不足以单独证明“禁止队伍打包”；是否允许安装、打包或调用第三方工具，
必须向赛事方确认。如果受限，再规划将内部验证适配到允许的工具链，
不要把未确认的权限当成当前方案已符合规则。

## 6. 私有题集、pass@k 与方案冻结

依据指南 3.1.2、3.1.4：

- VerilogEval v2 是建议的开发自测集，不是正式私有评测题集。
- 正式题量和构成赛前另行公告，私有集结果用于检验泛化。
- RTL 和 HLS 均报告 pass@1、pass@5，并希望减小两者差距。
- 评测窗口内不得修改代码、技能包或模型权重；提交哈希须与作品提交时一致。

当前 n=3、最多 3 轮的内部候选与反馈属于一次工作流；
不能把这些候选直接算成赛事的 pass@5。
未来按官方采样和时间预算记录独立运行，不能事后用官方测试台筛选最佳候选冒充单次输出。

开发阶段可以从失败中提炼通用技能、做改进实验并记录 journal；
私有集评测期间不能人工看结果后修改被冻结的方案。
预先提交的自动重试策略与临时改代码不同，但跨题缓存、在线记忆或经验更新的允许范围
仍应请赛事方说明。记录运行产物本身不能被表述为已获准修改技能包。

当前生成输入仅含题目和接口声明，参考正文和测试台只给独立评测器。
正式输入是否直接提供接口、何种工具反馈允许被智能体读取，也要按官方协议适配；
不能假设正式私有题一定提供当前公开集的参考文件。

## 7. NVIDIA 开发可行，最终必须覆盖 AMD 与离线交付

依据指南 2.5、3.1.2、3.1.3.1、4.3：

| 项目 | 指南要求或说明 | 当前状态 |
| --- | --- | --- |
| 开发平台 | 开发算力不限平台 | 当前 NVIDIA，以及后续 A100 开发均符合这一开发范围 |
| ROCm 验证资源 | W7900 单卡，48 GB | 未实测 |
| 决赛部署验证 | R9700，32 GB | 未实测 |
| 显存 | 模型须在单张 32 GB 卡内完整容纳，不跨卡；不按参数量设上限 | 双 4B 旧机采样约 29.49 GiB；其他硬件与负载待验 |
| 上下文 | 队伍自定，但须如实声明 | 当前 16384，需随最终提交固定 |
| 容器 | 基于官方基础镜像，在断网沙箱独立完成读题到产出代码 | 自有镜像、断网全流程尚未验收 |

W7900 有 48 GB、A100 可能有更大显存，都不改变 32 GB 的最终约束。
应核验两个模型以及缓存、工作空间的合计用量，并留出环境差异所需空间；
具体计量口径仍看评分细则。

离线交付要提前备齐模型、分词器、Python/GPU 依赖和获准工具，
验证启动及推理不依赖临时联网下载或远程模型服务。
容器模板和当前云平台容器不能代替基于官方镜像的验收。
两份 ChipMATE 权重存在 HF 访问条件，须确认赛事方的离线获取/交付方式；
不能把队伍个人账号凭据当作提交方案的一部分。

## 8. 模型、技能包与提交材料

指南 3.1.2、3.1.3.3、3.1.5 要求完整方案包含模型、推理栈、智能体、技能包与基线入口。

| 提交要素 | 应准备的内容 | 我们当前情况 |
| --- | --- | --- |
| Dockerfile | 继承官方基础镜像，可重建 | 只有待验收的开发模板 |
| model/MODEL.md | 模型来源与版本/校验和、量化、实测显存、上下文 | 已有双 4B 声明及 NVIDIA 证据，需补最终环境 |
| 智能体代码 | 控制流、重试与回退、上下文管理、工具编排 | 已复现固定上游并记录原始调用 |
| skill/ | 提示词、校验脚本、经验及适用条件，说明如何验证有效 | 当前只有说明性 README，尚无自有技能增益证据 |
| 推理服务 | 配置和启动入口 | NVIDIA 已验证，AMD 待验证 |
| run.sh / run_baseline.sh | 单题输出与同次基线，遵守官方协议 | 开发入口已有，正式协议与成对评测待补 |
| REPORT.md | 架构依据、模型选型、技能提炼、实测结果、失败分析、复现步骤 | 分散记录已有，正式报告未完成 |

直接使用已有硬件专用开源模型在指南中被允许；若自行微调，
需要开放微调权重，并声明基座、方法、训练数据来源和开源地址。

对工程质量和增益项，我的判断是：
当前 ChipMATE 复现可作为起点，但仅部署上游还没有证明我们自己的改进贡献。
应明确标注上游来源，针对可复现失败提出改动，通过消融或成对实验验证技能有效，
并说明代价和失效边界。不能把未实测技巧、公开题答案表或上游成果包装成自己的效果。

## 10. 接下来应优先补什么

遵守“旧服务器不追加单 4B/9B 测试，留到 A100”的既有决定，本次不启动任何新测试。

1. 先确认关键口径：双模型基线、第三方工具、同次运行、私有题接口、预算和采样规则。
2. A100 到位后，在相同硬件和固定数据/评测器上补同模型基线与双模型对照；
   单 9B 作为选型实验，固定模型身份后再测。保留原始 NVIDIA 结果。
3. 后续接入 Vivado 分级判定，先用已有输出分析 Icarus 与 Vivado 的差异，
   将评测环境修正和模型算法改进分开记录。
4. 围绕已确认的真实失败提炼技能包，用同模型基线和消融实验说明增益，
   同时记录生成预算、失败重试和墙钟时间。
5. 尽早完成一次 ROCm 可运行性检查，再完成目标 R9700、32 GB 与官方离线镜像验收。
6. 整理成可重建、可核验哈希的提交包与报告，冻结后遵守评测窗口规则。

这些是工程优先级建议，不代表上述工作已经完成或已经租用新服务器。
