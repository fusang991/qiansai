# 当前共识与阶段目标

## 已确认的选择

1. 采用方案二：独立比赛工程，固定版本保留 ChipMATE。
2. 只做 RTL；第一个模型方案为 ChipMATE V-4B 与 P-4B。
3. 当前先把本地架构做好；随后使用用户提供的 32 GB NVIDIA 云服务器部署原方案。
4. 原方案复现之后，再评估验证器改进、技能包和其他策略。Vivado 后续接入。
5. 从首次模型部署开始采用 Docker。初期一个容器内部有两个模型服务和工作流。
6. NVIDIA / AMD 共用业务代码与服务接口，分别维护 GPU 环境和设备配置。
7. 使用 Git 管理工程；上游与数据集使用固定版本子模块。
8. docs/ 下维护 context.md、decisions.md、architecture.md 三份核心文档；
   每次工作单独写入 docs/journal/，按时间和关键词命名。
9. 保留原始交流、操作、失败和结果；核心共识可更新，历史日志不被新摘要覆盖。
10. 测试统一使用 pytest；smoke 脚本仅组织数据检查与 pytest 调用。

## 当前参数约定

原版复现以 ChipMATE 根 README 的 Table 1 配置为起点：
n=3、max_turns=3、num_verify_tests=1000、temperature=1.0。
一次工作流最多含 18 份模型候选输出；记录完整工作流样本与单次模型调用的区别。
上游 paper_repro/ 中另有不同参数，不能无说明地混用。

serving.yaml 的 BF16、16384 上下文、单服务 0.45 显存比例和并发上限是待实机验证的
初始配置，不构成已经可部署的保证。两服务的权重、缓存和工作空间合计服从同卡预算。

## 已知问题与边界

- 上游端口解析存在 signed 和合并端口声明的局限。
- 上游交叉验证对双方缺失输出的处理存在假阳性风险。
- 第一阶段保留原版便于建立可复现参照；修复在独立改进版本中记录和验证。
- 自验证 match_rate 不是独立正确率。
- 双模型方案在正式增益评分中的裸跑口径等待后续细则；先保留 V-4B 单次生成入口。
- 官方镜像尚未提供；当前开发镜像模板不宣称满足最终提交条件。
